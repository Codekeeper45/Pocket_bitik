# Исправление и улучшение генерации изображений: план реализации

> **For Hermes:** Use subagent-driven-development skill to implement this plan task-by-task. Если такого навыка нет, найти доступный эквивалент и не выдумывать команды. Реализация начинается только после отдельного разрешения владельца.

**Goal:** Обеспечить соблюдение пользовательского замысла, сохранность референсов, геометрически корректный ремонт и честную оценку результата без послойной сборки.

**Architecture:** Telegram-обработчик остаётся тонким адаптером. Общая служба выполняет нормализацию запроса, подготовку контракта и референсов, цельную генерацию, ограниченный QA/ремонт и доставку. Одиночные арты, пакеты и серии используют общие типы данных, бюджеты и обработку ошибок.

**Tech Stack:** Python, asyncio, Telethon, Pillow, unittest, существующие Cliproxy и image gateway; новые инфраструктурные сервисы не требуются на первом этапе.

## Целевой пользовательский путь

Запрос -> проверка параметров -> контракт сцены -> реестр референсов -> промпт -> очередь -> цельный кадр -> техническая проверка -> QA -> оставить / локально исправить / один новый цельный кандидат -> доставка с честным статусом.

Обязательный контракт: тип задачи (создание/правка/серия), участники и количество, известная внешность, действие, композиция, обязательный текст, стиль, формат, роли референсов, неизменяемые требования. Неизвестную реальную внешность не выдумывать; при необходимости маркировать вымышленную интерпретацию.

## Метод выполнения каждой кодовой задачи

1. Добавить узкий воспроизводящий unittest с реальными Pillow-изображениями либо детерминированным mock API.
2. Запустить его, подтвердить падение именно на заявленной проблеме.
3. Реализовать минимальное исправление без побочного изменения художественного поведения.
4. Запустить узкие тесты и весь suite.
5. Провести ревью требований и кода, затем отдельный commit. Внешний deploy только через процедуру из последнего этапа.

Пути новых модулей ниже являются предлагаемыми. Не переписывать сразу весь `bot_new.py`; извлекать проверенные функции по одной.

## Этап 3. QA и политика ремонта

### Задача 5. Стабилизировать QA

Files: новый `gen_qa.py`, `bot_new.py:describe_image`, `_gen_visual_qa`, `_gen_repair_findings`, `tests/test_gen_qa.py`.

- Отдельный зафиксированный QA route на время job; переключение разговорной модели не меняет критерии посреди генерации.
- Проверка MIME в vision data URL: PNG не маркировать как JPEG.
- Схема finding: id, category, severity, confidence, bbox, affected_subject, requirement_id, description. Категории вместо поиска подстрок «рук», «лиц», «шов».
- QA failure/пустой невалидный ответ никогда не считать clean.
- Не скрывать findings после первых 12: лимит обоснован, overflow отмечается явно.
- Разделить fidelity пользовательскому контракту, техническую пригодность, анатомию, композицию и стилизацию.
- Приёмка: malformed JSON, отказ, unavailable, обязательный текст, стилизованные формы, серьёзный дефект без bbox.

### Задача 6. Парное сравнение и принятие ремонта

Files: `gen_qa.py`, `gen_repair.py`, `tests/test_gen_repair_acceptance.py`.

- Сравнить исходную и исправленную вырезки в одном вызове.
- Сравнить полный исходный кадр/лучший candidate с композитом, сохранив оригинальный контракт.
- Принятие: целевой дефект подтверждённо уменьшился; нет новых критичных defects, потери героя, изменения идентичности, обязательного текста или недопустимого шва.
- Число findings не использовать как единственную меру. Нельзя принять 2 medium -> 1 high.
- Качество края проверять также по градиентам/цвету в кольце области, но не делать один числовой score абсолютным арбитром.
- Feather по реальной зоне перехода; избегать смешения старых и новых контуров внутри дефектного объекта. Color matching/texture matching сначала ограниченный эксперимент.
- Всегда сохранять лучший candidate; failed improvement откатывается.
- Приёмка: mocked новые критические ошибки/швы/смена лица отклоняются; pixel tests плюс парные реальные примеры перед включением.

### Задача 7. Ограничить автоматический ремонт и перегенерацию

Files: новый `gen_policy.py`, `gen_repair.py`, `tests/test_gen_policy.py`.

- Локальная небольшая ошибка -> один bounded ремонт зоны.
- Глобальная плохая композиция, сломанная массовка, неверное количество героев -> максимум один новый цельный кандидат в автоматическом режиме.
- Мелкая спорная особенность -> оставить; не ремонтировать стилизацию автоматически.
- Сравнение candidates по контракту и отсутствию новых серьёзных дефектов; при недоказанном улучшении сохранять прежний.
- Явные бюджеты на gen calls, QA calls, wall time, refs и площадь ремонта. Значения подобрать по базовым замерам; стартовый кандидат для обычного запроса: не более двух локальных repair calls, без бесконечного цикла.
- Общий бюджет включает SDK retries и повторы шлюза; не считать только наружные вызовы.
- Исчерпание бюджета: честный итог со статусом warnings/unverified, не «всё исправлено».
- Приёмка: тесты всех переходов и исчерпания бюджета.

## Этап 6. Runtime и эксплуатация

### Задача 13. Общая очередь и deadline

Files: новый `gen_jobs.py`, `bot_new.py:_gen_rate_gate`, `_track_gen_activity`, handler, `tests/test_gen_jobs.py`.

- Общий semaphore для всех gen calls, включая repair, batch и series; rate limit отдельно от concurrency.
- Per-chat fairness; предельный размер очереди, queued/running статусы и приблизительное ожидание без ложной точности.
- Deadline каждого этапа и всего job, cancellation state. asyncio cancellation не отменяет requests в to_thread: учитывать незавершённый provider call, не высвобождать реальные ресурсы слишком рано.
- Централизовать retries: адаптер знает внешний gateway budget/SDK retry config, не умножать их скрыто.
- Persist jobs state/heartbeat/boot id атомарно; startup reconciliation вместо доверия старому jobs={}. После crash статус interrupted, не ложный idle.
- Не обещать отмену уже отправленной платной генерации, если backend её не поддерживает.
- Приёмка: несколько чатов и batch не превышают лимит, cancel/fail не оставляет lock, stale boot/activity обнаруживается.

### Задача 14. Доставка и наблюдаемость

Files: `gen_jobs.py`, `_gen_send_image`, handler, `docs/gen-regional-layers.md`, новые `tests/test_gen_delivery.py`.

- Correlation job id на всех стадиях; версия prompt/schema/model/provider, actual dimensions, stage durations, call counts, findings и решение repair.
- Не логировать secrets, полные payloads и пользовательские фото без необходимости.
- Ошибка доставки вызывает повтор доставки из сохранённого результата, не новую generation.
- В Telegram превью и возможность получить оригинальный файл без photo compression; не присылать каждый оригинал дополнительным сообщением по умолчанию.
- Не удалять пользовательскую команду без прямого запроса. Служебные статусы очищать отдельно; не скрывать error/warnings сразу после появления.
- Артефакты в изолированном project path с TTL/квотой и минимумом персональных данных; пользовательские фото для QA временно и с удалением после проверки.
- Приёмка: delivery timeout, flood wait, status cleanup failure, original download, data retention.

### Задача 16. Проверить улучшения отдельно

- Два цельных candidates для сложной сцены против gen+repair: качество/время/стоимость; best-of не включать всем по умолчанию.
- Multi-scale QA: общий кадр плюс selected zooms, а не отдельный платный вызов на каждого человека.
- OCR точного обязательного текста; обычный typography renderer для отдельных подписей только если композиция и просьба допускают. Не перерисовывать произвольный текст на предметах вслепую.
- Мягкая цветовая/фактурная согласовка repair, support настоящей mask edit после capability probe, не текстовая псевдомаска.
- Отдельный upscaler с визуальными тестами: новые детали и лица могут искажаться, апскейл не обязан улучшать.
- Роутинг моделей по типу сцены только после сравнительного benchmark и отдельного решения владельца. Не менять рабочую модель из-за единичного сбоя.
- Контактные тени/перспектива/толпа проверяются в цельном кадре; послойный montage не возвращается.
- Приёмка: documented experiment result и решение enable/disable; отрицательный результат допустим, недоказанную функцию не деплоить.

## Safe deploy и rollback

- Исходная ревизия/файлы/конфиг имеют восстановимый backup в проекте; secrets не в git.
- Commit и push каждой завершённой логической группы. Проверить `git ls-remote origin refs/heads/main`.
- Не рестартовать активные генерации. Атомарно закрыть приём новых jobs, дождаться завершения текущих и проверить heartbeat, boot id, activity, logs; одной проверки пустого JSON недостаточно.
- Deploy unit как согласованный набор файлов/requirements/config. Проверить загрузку и readback, зависимости и startup.
- Вернуть приём jobs после health-check. Боевой smoke в чате владельца: один простой цельный арт и один сложный кейс по текущему релизу; читать exact delivered message, осмотреть image.
- Для серий отдельно проверить short story и отказ страницы; для repair отдельно before/after и pixels outside.
- Rollback при critical regression возвращает предыдущий code/config, без повторной отправки оплаченных jobs. Drain перед rollback, если процесс работоспособен.
- Отчёт: Serverix ID, GitHub branch/commit, actual deployed revision, paths, exact tests/results, реальные latency/calls, известные ограничения.

## Итоговые критерии готовности

- Послойная генерация остаётся выключенной.
- Все unit/integration tests зелёные; каждый заявленный найденный баг имеет regression test.
- Размер/соотношение сторон и original delivery не вводят пользователя в заблуждение.
- Repair не растягивает crops, не теряет alpha, сравнивает before/after и откатывает новые critical defects; вне repair box декодированные пиксели совпадают.
- Обязательные участники/имена/текст и user orientation сохраняются; refs имеют доказуемую связь с endpoint order.
- Нет молчаливого размножения страниц и выдуманных причин ошибки; retry delivery/resume не дублирует generation.
- Очередь и budgets проверены под параллельными mock jobs; interrupted/stale состояния распознаются.
- Live acceptance опирается на реальные картинки и боевые сообщения. Unavailable QA явно отмечается, warnings не выдаются за идеальный результат.
- По контрольному набору нет явной регрессии; экспериментальные improvements включаются только после доказанного выигрыша.
