# Аудит навыков для `/gen`: формирование промптов изображений

**Область:** публично доступные релевантные навыки из обнаруженного окружения и целевого поиска, не «все существующие навыки». Проверены первичные тексты `SKILL.md` через `raw.githubusercontent.com` и GitHub API; без установки и запуска сторонних скриптов. Это аудит рекомендаций, не изменение поведения бота.

## Вывод для интеграции

Строить `/gen` вокруг короткого, контролируемого перевода запроса в визуальный бриф, а не вокруг копирования рецептов одной модели. Приоритет: **намерение пользователя > подтверждённые ограничения текущего генератора > выбранный медиум > эстетические улучшения**. Не дописывать объекты, сюжет, бренд, настроение или композиционные стороны, которых пользователь не подразумевал. Подробный запрос структурировать, не раздувать; расплывчатый уточнять через минимальные решения, явно служащие задаче.

Предлагаемые поля внутреннего брифа (применять выборочно):
1. **Что изображено / главное действие** — субъект первым, конкретные визуально существенные признаки.
2. **Где и как соотносится с окружением** — фон, глубина, пространственные отношения.
3. **Кадрирование / композиция** — крупность, точка зрения, размещение и отрицательное пространство, только если они значимы для задачи.
4. **Медиум / визуальный язык** — фото, иллюстрация, 3D и т.п.; стиль согласован с намерением.
5. **Свет, цвет, настроение, фактура** — только информативные, непротиворечивые детали.
6. **Точный текст** — дословно, в кавычках, без добавления выдуманного текста.
7. **Инварианты / исключения** — что сохранить и что исключить; передавать только если инструмент поддерживает соответствующую семантику.
8. **Формат / применение** — соотношение сторон/композиционное пространство, когда известно из запроса или подтверждённой схемы.

Перед выдачей сверить промпт с запросом: главный объект и действие сохранены; нет выдуманных элементов; композиция/стиль не конфликтуют; точный текст точен; параметры инструмента проверены. Для редакции одного изображения — сохранять перечисленные пользователем инварианты и формулировать изменение адресно. Итерации — по одному целевому изменению за раз.

## Принципы: принять, адаптировать, отклонить

### Принять как общие статичные правила
- **Сначала намерение, затем спецификация:** задача/субъект → важные особенности → место и отношения → при необходимости кадр, стиль, свет. Структура — внутренний чеклист, не обязательный шаблон для каждого пользователя. (Codex; частично inference prompt-engineering.)
- **Точность без самодеятельности:** сохранять содержание запроса и не добавлять детали, которые меняют нарратив. При конкретном промпте — нормализовать, не «улучшать»; при общем — только низкорисковая конкретизация, реально улучшающая визуальную определённость. (Codex.)
- **Композиция — конкретные наблюдаемые указания:** крупность/ракурс/точка зрения, положение главного объекта, foreground/background и свободное место там, где это важно. Выбирать конкретную композицию под задачу, а не пустое «красиво/кинематографично». (Storyboard, prompt-engineering, taste web как примеры.)
- **Согласованность и редактирование:** в многокадровых/повторных изображениях повторять только важные признаки идентичности/визуального языка; при edit назвать, что меняется, и что остаётся неизменным. (Storyboard, anime-AMV, Codex.)
- **Сдержанность:** убрать противоречия, лишние синонимы/прилагательные, SEO-подобные «8K masterpiece best quality» и нерелевантную стилистическую мишуру. Проверять соответствие исходному brief, не заменять его эстетической оценкой. (Сопоставление источников; prompt-engineering сам содержит такие keyword-листы, но не доказывает их универсальную эффективность.)
- **Явный текст:** точный текст переписывать дословно, требовать только если пользователь просит текст в изображении; если нет — не придумывать надписи. (Codex и модельно-специфичный пример RunComfy — принцип задачи, не API-параметр.)
- **Референсы:** определить их роль (объект/личность, композиция, стиль, палитра); не смешивать все роли без указания пользователя. Соблюдать приоритет его референса над эстетическим пресетом. (Codex.)
- **QA после генерации:** сравнить с запросом по субъекту, стилю, композиции, читаемости букв и инвариантам; если нужна правка — одна направленная правка за итерацию. Применяется к `/gen`, только если бот реально умеет анализировать результат; иначе не обещать авто-QA. (Codex.)

### Применять только при совпадении задачи
- **Taste web:** разнообразить композиции вместо автоматического «текст слева, картинка справа»; свободное пространство, читаемая иерархия, контролируемая палитра, меньше клише. Хорошо для website reference images, но не ставить baseline variance 8, обязательные full-bleed, narrative spine, CTA/конверсионные блоки или «одна картинка на каждую секцию» для обычного изображения. Все baseline values и жёсткие output counts — авторские пресеты, не эмпирические правила.
- **Taste mobile:** учесть platform-native детали, safe areas, читаемость, логичный поток и системную консистентность — только если пользователь просит UI экраны/поток. Не навязывать iPhone mockup, число кадров, генерацию дополнительных экранов и мобильный арт-дирекшн для произвольной картинки.
- **Brandkit:** начать с значения бренда/аудитории и связать метафору, знак, палитру и применения; сетка/ритм/негативное пространство и малое число цветов полезны для бренд-борда. Не переводить в обязательный 3×3, тёмный холст, логотип в каждой панели, фиксированную палитру или «премиальность» без запроса.
- **Storyboard:** использовать shot vocabulary только когда помогает обычной композиции; continuity/ось/разнообразие планов — при создании последовательности с персонажами или storyboard, не одиночного статичного кадра.

### Отклонить как неподтверждённое или неприменимое
- **Не зашивать** параметры и синтаксис `negative_prompt`, FLUX LoRA, `steps`, seeds, widths/heights, `aspect_ratio`, `quality`, сторонние CLI-команды, названия моделей или цены из стороннего навыка. В частности, prompt-engineering предлагает `negative_prompt` для FLUX, тогда как проверенный inference skill описывает несколько провайдеров и не утверждает поддержку поля в нашем шлюзе. Использовать параметры лишь после проверки актуальной схемы реального `/gen` backend.
- **Не переносить** длительности видео, движение камеры как движение, beat timestamps, 70/30 shot rule, 180° continuity как требования одиночной картинки, fps/FFmpeg/Flow/внешние `belt`/`runcomfy` CLI и платные сервисы. При необходимости слова о ракурсе/кадрировании переосмысливать как статичные свойства кадра.
- **Не делать универсальными** композиционные запреты/предписания Taste («всегда отдельная картинка на секцию», 3+ разных якоря, конкретное число экранов/компонентов, обязательный device frame/full bleed). Это может противоречить запросу.
- **Не добавлять** имена реальных художников/брендов, «film stock», 4K и декоративные стили без связи с brief. Источник упоминает их как примеры/keywords, не как гарантированные инструкции.

## Рекомендации реализации для владельца `/gen`

1. Сделать компактный intent-preserving prompt composer, где поля необязательны и не заставляют добавлять детали.
2. Отделить базовые языковые правила от backend-specific параметров. Последние включать только по проверенной конфигурации gateway, не по чужим рецептам. Текущая маршрутизация на GPT Image 2 не считается подтверждением реального модели/API.
3. UI/бренд/storyboard режимы включать только когда пользователь просит соответствующий тип результата; никаких автоматических изменений числа генераций или содержания.
4. Проверять пользовательские требования в готовом промпте и не делать художественный пресет сильнее намерения. Для точного текста/исключений — буквальная передача.
5. Сохранить этот документ как source ledger; он не редактирует bot code и не утверждает, что перечень источников исчерпывающий.
