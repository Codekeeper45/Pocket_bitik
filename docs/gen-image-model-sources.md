Дата проверки: 2026-10-05. Цель: подготовить базу знаний для Gen, не менять код и не генерировать изображения.

## Краткий вывод об идентичности модели

**Подтверждено официальной документацией OpenAI:** модель API существует под точным именем `gpt-image-2` (также snapshot `gpt-image-2-2026-04-21`). Официальное руководство называет её GPT Image 2. В API Image Reference также перечислены имена `gpt-image-2.5-sunburst` и `gpt-image-2.5-flare` (включая snapshots `...-2026-09-08`); следовательно, Sunburst не является лишь названием, которое нигде не встречается в публичной документации OpenAI.

**Не подтверждается одним только именем в Gen/шлюзе:** что текущий alias `gpt-image-2.5-sunburst` действительно направлен на официальный upstream OpenAI, какой именно snapshot обслужил запрос, или что любые результаты шлюза тождественны GPT Image 2. Требуется проверить конфигурацию/ответ upstream и логи маршрутизации (model returned/route metadata), а при сравнении вести контрольные тесты. Образцы cookbook используют конкретные названия моделей и не доказывают идентичность любого proxy alias.

Важное различие: актуальное руководство для общих prompting-приёмов — официальная страница Image Prompting; она отмечает, что примеры иллюстрируют GPT Image 2.5 Flare/Sunburst и результаты могут различаться между моделями. Cookbook prompt guide помечен как архивный/может содержать устаревшие API/модели. Использовать его как набор workflow-примеров, а не как нормативный источник текущих параметров.

## Что взять для Gen: устойчивый слой промптинга

### 1. Сохранять пользовательскую архитектуру; структурировать, не перепридумывать

Порядок: **сцена/фон → субъект → ключевые детали → ограничения → назначение результата**. Для сложных задач использовать короткие маркированные поля, а не бесформенный длинный текст. Существующую art-библию/архитектуру композиции Gen следует сохранять и не заменять общим шаблоном. Нормализация означает перенос уже заданных требований в ясные поля, не удаление смысла и не добавление новых объектов, цветов, слоганов, персонажей или сюжетных битов.

Рабочие поля, применять по необходимости:
- Задача / назначение; вид актива
- Входные изображения и **роль каждого**
- Сцена/фон; субъект/действие
- Стиль/носитель, композиция/камера, свет/настроение, палитра/материалы
- Точный текст (verbatim) и размещение/типографика
- Ограничения и исключения

Это scaffold, не обязательный жёсткий JSON schema. Для уже насыщенного композиционного промпта — не дублировать поле за полем и не менять детали ради формы.

### 2. Правки: отделить изменения от инвариантов

Для edit писать явно: **«измени только X; Y и Z оставь неизменными»**. Повторять критичные инварианты при каждом уточнении, например идентичность персонажа, лицо/тело/поза/волосы, кадр, фон, палитру, одежду и уже верные детали. Обозначить, что именно редактируемая цель, а что reference. После базового результата вносить по одному целевому изменению; не переписывать весь промпт при каждом шаге. Сохранять исходник/версии неразрушающе.

### 3. Мульти-референсы: указать индекс и назначение

Каждому входу дать номер и роль, например:
- Image 1 — редактируемая база; сохранить кадр и персонажа.
- Image 2 — референс внешности персонажа; брать только черты/одежду.
- Image 3 — style reference; перенести фактуру/палитру, не композицию.

Для композита описать отношение явно: что из какого изображения переносится, куда, с каким масштабом/перспективой/светом. Не считать каждую прикреплённую картинку целью редактирования. Если изображения лишь для стиля/композиции, это generate with references. Никакого автоматического смешения «стиль + идентичность + layout» без указания приоритета. Для повторяющегося героя явно фиксировать видимые инварианты внешности и стиля на каждом кадре/итерации.

### 4. Точный текст и геометрия макета

Текст в кавычках или ALL CAPS, дословно; задать шрифт/характер типографики, размер/контраст, положение относительно конкретного объекта/края/секции. Для редких/важных слов допустимо spelling letter-by-letter. Требовать ровно заданные символы, без лишних надписей. Для инфографики перечислить подписи и структуру/порядок блоков отдельно. Не обещать 100% точность: проверять рендер букв и размещение визуально и точечным edit исправлять только неверную надпись, сохраняя сетку.

### 5. Толпа, повторяемые фигуры и художественная консистентность

Источники рекомендуют конкретные действия/сценические биты, ясные панельные/пространственные структуры, а также повторение инвариантов. Практический вывод для Gen: если нужна толпа, конкретизировать общий масштаб и уровни глубины, разнообразие поз/одежды, плотность и читаемый передний план; при этом явно удерживать единый художественный стиль, освещение и перспективу. Персонажей/детали толпы не изобретать, если их не подразумевает задача. Это прикладная рекомендация для текущего случая Gen, а не специальное гарантийное правило GPT Image 2 из API.

### 6. Стиль и композиция без конфликта

Формулировать стиль через наблюдаемые признаки: medium/материалы, линия/кисть/рендер, палитра, контраст, свет. Камера/ракурс/крупность и свободные поля задаются только если влияют на задачу; не вводить произвольное «слева/справа», если это не следует из референса/макета. Если правка style-transfer, чётко назвать, что переносить (например фактуру и палитру), что менять и что оставить, добавить запрет на лишние элементы. Существующие правила Adobe/Clip Studio/Disney и композиционная библиотека Pocket_bitik должны оставаться отдельными утверждёнными источниками проекта; документация OpenAI их не заменяет.

## Рекомендации для интеграции с текущим Gen

1. Добавить этот документ как **source/research guide**, не менять бот-код в рамках исследования.
2. В prompt-builder сохранить исходную структуру композиции и художественные ограничения Gen; использовать OpenAI правила как слой уточнения и QC, не как новый универсальный шаблон вместо проекта.
3. Разделить режимы `generate` и `edit`; для edit требовать карту «что меняется / что неизменно».
4. Передавать модели явные роли reference-изображений и приоритеты между ними; не полагаться на порядок файлов без текстовой маркировки.
5. Проверять точные надписи и их положение отдельным QA; crowd/series-consistency вынести в чеклист, не утверждая гарантии модели.
6. В runtime/logging отделять имя, которое запросил Gen, от подтверждённой upstream модели/snapshot. Не записывать `gpt-image-2.5-sunburst` как «точно GPT Image 2», пока нет подтверждения маршрута; хранить requested model, returned/effective model если доступно, provider, timestamp и результат проверки.
7. Для актуальных API параметров сверяться с live API reference, а cookbook использовать для идей/примеров. Не копировать параметры `input_fidelity` и другие настройки из старых моделей в GPT Image 2: актуальная страница просит не задавать `input_fidelity` для GPT Image 2.

## Provenance: проверенное и предположительное

**Проверено непосредственно по официальным страницам:** точные API имена `gpt-image-2`/snapshot; edit-reference официально перечисляет Sunburst/Flare aliases и snapshots; требования API к размерам; роль `input_fidelity` в руководстве GPT Image 2; предупреждение, что cookbook архивный; тексты OpenAI imagegen skill и prompting references.

**Не проверено в этом исследовании:** реальный upstream Gen на данный момент, значение внутреннего alias `gpt-image-2.5-sunburst` в установленной конфигурации/Cliproxy, доступность моделей аккаунту, точное поведение на проектных композициях, художественная точность персонажей и точность конкретной типографики. Нужны лог/метаданные реального запроса и контролируемый eval на текущем маршруте.

**Ограничение охвата навыков:** изучен официальный `openai/skills` системный imagegen и его две prompting reference. Это не утверждение, что найден/прочитан весь мировой набор image-generation skills; в рамках этой задачи охват — относящиеся к генерации официальные материалы OpenAI.
